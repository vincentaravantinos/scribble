# CR-004: Faster large-area erase via modifyPageElements

**Status:** Rejected

## Request

Idea from r/Supernote_dev (u/dimmir, on the Chauvet 3.29.43 SDK release
thread): the new `PluginCommAPI.modifyPageElements`/`batchUpdatePageElements`
APIs (added in the same release CR-001/002/003 adapted to) might let erase
avoid its current per-element delete pipeline and speed up large-area
scribbles, which today take noticeably longer than small ones (per
dimmir's report: "quite fast for small bits, but sometimes I'd like to
erase around a quarter of the page and it seems to take an exponentially
longer time").

Not scoped or committed to yet — this CR is to investigate whether these
APIs are actually usable for this and, if so, how much they'd help.

## Impact analysis / rejection

**Rejected — premise doesn't hold, no spike needed.** `erase.ts`'s actual
delete step (`lassoElements` → `getLassoElements` → `deleteLassoElements`)
is already a single batched round-trip per call, independent of how many
elements are selected. `modifyPageElements`/`batchUpdatePageElements` are
also single batched calls — swapping one O(1)-round-trip batch delete for
another can't meaningfully change delete-step latency.

The actual scaling cost lives earlier: `getElements` reads the whole page,
then every element passing the scribble's bbox prefilter pays its own
`readStrokePoints` bridge call plus a `polylinesCross` check — this scales
with the scribble's bounding-box area, which matches dimmir's "quarter of
the page... exponentially longer" report far better than the delete step
does. Real numbers from this session's own on-device testing back this:
`readMs` (covering `getElements` + the candidate loop) was 370–900ms on
pages with only 4-6 elements.

None of the Chauvet 3.29.43/2.26.40 release's new or changed APIs touch
reading elements or stroke points faster — the new APIs are all writes
(`modifyPageElements` et al.) or unrelated (permissions, `jumpToPage`,
`openFile`, etc.). SPEC.md's existing "Cost of finding candidates" note
already identifies the only real lever as a native module handling the
read/crossing-test off the JS bridge — a separate, much larger
undertaking this SDK release doesn't provide. No undo-safety spike was
needed since the premise was ruled out first.

If large-area erase performance is worth chasing later, it should be
scoped as its own CR targeting the read/candidate-scan step specifically
(and likely requires profiling to split getElements time from the
per-candidate loop time), not this one.
